# frontend-agent-lab POC 建设与验证记录

本文只记录 `frontend-agent-lab` 仓库的具体工具映射、建设进度和验证任务，不属于通用规则。

跨项目、跨框架的流程定义以[前端 AI 自动化工作流手册](ai-frontend-workflow.md)为准；示例需求以 [GitHub Issue #1：根据已有食材推荐菜谱](https://github.com/htk5257577/frontend-agent-lab/issues/1) 为准；可执行验证任务见 [GitHub Issue #2](https://github.com/htk5257577/frontend-agent-lab/issues/2)。

## 1. 本仓库的工具映射

| 工作流能力    | 本仓库实现                                      |
| ------------- | ----------------------------------------------- |
| 包管理器      | pnpm，版本由 `package.json#packageManager` 固定 |
| 运行时        | Node.js，版本由 `package.json#engines` 固定     |
| 类型检查      | vue-tsc                                         |
| 代码问题检查  | ESLint                                          |
| 格式          | Prettier                                        |
| 单元/组件测试 | Vitest                                          |
| 浏览器测试    | Playwright                                      |
| 任务追踪      | GitHub Issues + labels                          |
| 远程门禁      | GitHub Actions                                  |
| 设计事实源    | 最终批准的 Penpot 版本                          |
| AI 设计输入   | Issue、上游资料和本地参考原型                   |
| 最终合并权限  | 人工审核并手工合并                              |

固定命令：

```bash
pnpm install --frozen-lockfile
pnpm run dev
pnpm run fix
pnpm run check
pnpm run check:all
```

## 3. 后续建设顺序

1. **接通上游资料**：用脱敏 Jira Case 和 Confluence 页面补充 Issue #1，验证权限、精确版本、附件和冲突处理。
2. **建立正式设计**：创建 Penpot 文件，通过官方 MCP 让 AI 参考而不复制本地 A/B/C，生成 2–3 套新候选；由人选择并记录准确版本和 `.penpot` 备份。
3. **验证任务输入**：分别使用 Feature 和 Bug 模板，确认原始输入、来源、设计信息和复现证据能支持 DoR 判断。
4. **验证真实 PR 门禁**：在普通分支制造一次可恢复失败，确认 GitHub Actions 变红；修复后确认新 head SHA 的 `ci`/`e2e` 恢复绿色，并能取得失败证据。
5. **配置主分支保护**：将验证过的检查设为 required，禁止直接推送和机器人自行合并，并要求至少一名人类 reviewer。
6. **跑通最小自动执行**：先使用手工触发，从一个已批准 Issue 创建隔离分支、实现、验证和 Draft PR；最终仍由人处理失败和合并。
7. **加入独立 AI 审查**：建立 Standards 与 Spec 双轴检查，再加入最多两轮的自动修复和重新审查。
8. **补齐 UI 验收**：接入预览环境、批准视口截图和视觉回归，对照准确的 Penpot 批准版本。
9. **补齐上线反馈**：记录部署、冒烟、监控、回滚或重开 Issue，并关联 run ID、PR、commit 和设计版本。
10. **逐步开放无人值守入口**：多个真实任务稳定后，才允许 `ready-for-agent` 标签触发执行，并增加任务锁、幂等和失败恢复。
11. **最后适配内部 GitLab**：先检查公司实例的 webhook、runner、审批、保护规则和 service account，再替换平台 adapter。

当前不建设自动合并。所有机器检查通过后，仍由人完成最终审核和手工合并。

## 4. 用食材推荐需求验证工作流

Issue #1 是本 POC 的示例规格。GitHub Issue 是开发执行记录；Jira、Confluence 和 Penpot 是可追溯的上游来源，不能各自维护一份互相漂移的最终需求。仓库公开，只能使用脱敏测试资料和非敏感设计。

### 4.1 验证清单

| 验证点        | 要实际做什么                                                                      | 必须留下的证据                                        | 通过标准                                                                    |
| ------------- | --------------------------------------------------------------------------------- | ----------------------------------------------------- | --------------------------------------------------------------------------- |
| GitHub Issue  | 保留原始输入，补齐目标、范围、范围外、验收标准、依赖和验证方法                    | Issue URL、编辑/评论历史、标签变化                    | 聊天不是唯一来源；信息不足时停在 `needs-info`                               |
| Jira Case     | 读取一个脱敏 Case、评论和附件，在 GitHub Issue 中记录准确 key、链接和读取时间     | Jira key、读取时间、反向链接或脱敏快照                | AI 能区分当前结论与历史评论，不复制出第二份失控规格                         |
| Confluence    | 用脱敏页面补充业务规则，并记录页面版本或更新时间                                  | 页面链接、版本/更新时间、采用的结论                   | AI 读取准确页面；页面变化会触发规格重新评估                                 |
| 来源冲突      | 在测试资料中制造一个无风险规则冲突                                                | 差异清单、负责人结论和回写位置                        | AI 不猜测优先级，冲突解决前保持 `needs-info`                                |
| Penpot MCP    | 创建 Penpot 文件，先验证 AI 只读获取页面和组件，再授权小步写入                    | 文件链接和只读验证结果；不得记录 MCP 密钥             | AI 操作正确文件和页面，能够读取并创建节点，密钥没有泄露                     |
| Penpot 新候选 | AI 根据 Issue 重新生成 2–3 套有实质差异的候选；本地 A/B/C 只作参考                | 每套方案的页面/对象链接、状态和视口清单               | 差异来自交互、信息层级或视觉系统，而不是只换颜色                            |
| 设计选择      | 人选择一套或明确组合规则，补齐主路径、状态、响应式、文案、资源和无障碍            | 选择人、时间、准确 Penpot 版本、备份和 Issue 更新     | 交互、布局、主题都有明确依据，实现 agent 不需要继续做产品或 UI 决定         |
| DoR 与批准    | 按 Definition of Ready 检查规格、设计和依赖                                       | 检查结果与明确批准评论                                | 没有高影响未决问题，此时才能添加 `ready-for-agent`                          |
| 任务拆分      | 需要时按纵向可验证结果拆票并标出依赖                                              | 父规格、tickets 和阻塞关系                            | 每张票能独立交付可验证结果，不按技术层制造空任务                            |
| 代码一致性    | 在隔离分支中测试先行，实现最小完整改动并运行固定门禁                              | commit、测试和 `pnpm run check` 结果                  | 遵守通用手册的代码一致性规则，没有无关 diff、工具绕过或直接复制参考原型上线 |
| GitHub CI     | 创建 Draft PR，制造一次可恢复的格式或测试失败，再修复并推送新 commit              | 红色与恢复绿色的 Actions run、失败证据和最终 head SHA | 冻结 lockfile 安装；失败会阻塞；新 commit 不继承旧结果                      |
| 主分支保护    | CI 验证后，把固定门禁和未来的 AI review 设为 required，要求人工批准并禁止直接推送 | Ruleset/branch protection 截图或 API 结果             | 检查失败、缺少人工批准或有阻塞讨论时无法合并，机器人没有绕过权限            |
| 独立 AI CR    | 使用未参与实现的上下文分别进行 Standards 和 Spec review                           | findings、文件/行、严重度和审查状态                   | blocker/major 会阻塞；修复后针对新 SHA 重跑；自动修复最多两轮               |
| 人工合并      | AI 与 CI 通过后，由人核对需求意图、UI、风险和回滚并手工合并                       | 人类批准、merge SHA 和未决风险                        | 不启用自动合并；新 commit 后旧批准失效                                      |
| 发布与反馈    | 运行预览或测试部署、关键路径冒烟，并模拟一次失败回滚或重开 Issue                  | 部署版本、冒烟、回滚或 verified 记录和周期指标        | 健康后才关闭原任务；异常能够回到分诊或诊断，同时保留全链路追溯              |

### 4.2 重点观察的失败方式

- AI 是否因为能看到聊天而跳过 Issue 持久化。
- Jira 或 Confluence 无法访问时，是否请求连接或脱敏导出，而不是假装已经读取。
- 来源冲突时，是否停止并要求人决定，而不是按工具名称自行排序。
- Penpot 是否先读后写、小步可撤销；AI 是否把本地 A/B/C 错当成批准设计。
- `ready-for-agent` 是否在设计和人工批准前被过早添加。
- 本地、agent 与 CI 是否使用同一套 pnpm 命令。
- CI 是否验证最终 head SHA，失败证据是否足以诊断。
- AI CR 是否独立并能发现规格偏差，而不只是重复 lint 输出。
- 人工是否始终掌握最终合并权限。
- 失败后是否回到正确阶段并保留需求、run、分支、PR、commit 和设计版本的关联。

### 4.3 POC 通过条件

- GitHub Issue、Jira、Confluence、Penpot 和 PR/CI 能追溯到同一个需求 ID。
- AI 在 Penpot 中生成新候选，人完成选择并记录准确批准版本；本地 A/B/C 始终只是参考。
- 规格与设计批准前，Issue 不会进入 `ready-for-agent`。
- 实现通过统一代码规则、本地门禁、远程 CI 和独立 AI CR。
- 至少验证一次可控失败、诊断/修复和重新检查，而不只验证成功路径。
- 最终合并由人完成，合并后有可重复冒烟、异常反馈和回滚路径。
- 所有测试资料均已脱敏，没有把内部数据、设计或平台凭据放入公开仓库。
